# Local invoice pilot implementation plan

The release should let a staff member select a project, establish its rules, check a named invoice in Claude or Codex, verify the evidence, and export a confirmed decision. Existing local projects and reviewed records must remain usable.

| Order | Work and decisions | Release check |
|---|---|---|
| 1. Separate shipped files from staff data | Document file ownership and backup scope. Store the example setup as an importable template outside live projects. Keep existing local project files at their paths, protect live projects from Git, and exclude reviewer tips and proposal history from the shipped template. Preserve manually added skills and unrelated configuration during synchronization. Make desktop startup use the workspace runtime. | Compare project data before and after. Exercise the template, skill sync and recovery in a disposable installation. A synthetic project must still open and export after restoring its folder. |
| 2. Pin the project and identify invoices | Send an explicit project with site data requests and specify a project for chat commands. Keep the project selector as a default for starting a task. Preserve existing invoice IDs, allocate distinct IDs for same-stem uploads across formats and handle existing collisions. Supply a usable starter document type and fields for new projects. | Open the same invoice name in two projects, switch projects, then save. Verify the intended project is updated. Upload same-stem files in two formats and open both independently. Start from an empty workspace. |
| 3. Protect review decisions | Distinguish zero applicable rules from a pass in UI and Excel. Stage rechecks of confirmed records separately, present the candidate for review, and update the official result only upon explicit acceptance. Retain prior confirmed decisions and keep published exports stable while a candidate is pending. | Correct an amount, confirm, recheck twice and export. The confirmed amount must persist until the reviewer accepts the candidate. Verify results with zero rules and results where all applicable rules pass. |
| 4. Simplify the reviewer experience | Make invoices and project setup the main destinations. Keep Help, history and settings reachable. Provide a dedicated invoice view with a back action, continuous pages, keyboard/click evidence selection, classification rationale, questions, separate values and findings, and explicit corrections. Show the effect of a correction versus a project tip. Lead setup with guideline approval and allow creating types and fields. | Walk from a fresh project to a reviewed invoice. Verify evidence navigation across pages, draft and confirmed review, returning to the list and preserving edits during background refresh. |
| 5. Connect chat, reporting and handover | Prepare copyable requests for the selected invoice, finding or pending batch with the exact project and invoice IDs. Make the project workbook and individual marked PDF easy to distinguish. Provide a copyable confirmed row using the existing workbook columns and readable, selectable history for pilot feedback. Keep the setup transfer separate from results. | Inspect copied prompts, workbook rows, marked PDF and history. Open a second project and check that the links and exports still refer to the original selection. |
| 6. Verify and document | Add regression coverage for the risks above. Run the suite, skill drift check, an isolated workflow with generated documents, and browser smoke checks. Update help, skills and README to describe what actually shipped and how to recover local data. | Record evidence, residual limitations and work that depends on access to staff devices or documents. |

### Delivery and verification — 24 November 2026

All six implementation steps are in the local checkout. The [file structure audit and recovery instructions](README.md#file-structure-audit) explain which files belong to staff and how to move an existing installation. The [reviewer guide](README.md#a-normal-week) describes the updated controls.

- **Data and compatibility.** Project-scoped saves, distinct upload IDs, legacy filename collisions, stale reviews and failed imports have automated coverage. Rechecks preserve the last confirmed amount and marked PDF until acceptance. Older records that had already lost an original reading or mark before this release may still be incomplete.
- **Website.** Two Chrome smoke workflows ran against the modularized website and local Python API using disposable invoices. They exercised fresh project selection, page-two evidence, contextual copy requests, field correction, confirmation, setup changes, candidate comparison and acceptance. A delayed response from a second project did not replace the open invoice. The updated page and its modules also loaded from the normal local server.
- **Installation and recovery.** All 25 tests passed in a fresh virtual environment using the locked dependencies and an available local Python installation and package cache. Both assistant skill installations passed the drift check. Restoring a synthetic project into the fresh installation reproduced its corrected amount and confirmed status in Excel. Comparison against the original checkout verified the contents of all 72 live project files.
- **Sharing.** The downloadable workbook covers the project, and a confirmed row can be copied for one invoice. The pending staff template review determines whether the current column order fits the team's register. Chat buttons prepare a request that the reviewer pastes into the chosen assistant.

### Decisions requiring a staff pilot

Observe one real invoice being recorded in the team's register and one partner interpreting a marked PDF. Use that evidence to finalize the spreadsheet columns, decide on a findings cover sheet or editable boxes, and compare chat upload with page upload. Shared Drive writes, live multi-user synchronization, an embedded chat or plugin, model delegation and self-modifying workflows require separate product decisions. A field trial on staff Windows and Mac machines and a week of ordinary use are the final adoption checks.
