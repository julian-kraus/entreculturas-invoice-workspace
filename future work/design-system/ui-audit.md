# UI and shared component audit

The first audit exercised the website in headless Chromium with synthetic project and settings responses. The findings below distinguish that browser evidence from inspection of the current branch. See the [design proposal](README.md) for the corresponding component and interaction contracts.

## Improvements in the current branch

- **Uploads, setup filters and dialog names.** The upload result lists every filename and outcome with a retry for failed files. Setup filters retain focus and open disclosures for items still visible. New project and the clipboard fallback have named dialogs. Chrome verified a mixed upload, a filtered rule disclosure and the New project label. [Upload helper](../../app/workspace.js), [Setup filters](../../app/project-setup.js), [New project](../../app/index.html)

- **Editable Inbox and batch decisions.** Chromium covered typed proposal edits, approving a filtered batch, canceling the confirmation, preserving other drafts and reviewing a stale item after partial success. An incomplete field-based check focuses the missing field. The server also validates edited check settings before confirmation. Decisions appear beneath the setup title. [Inbox](../../app/project-setup.js), [server validation](../../app/server.py)
- **Concurrent setup writes.** Browser edits, Inbox decisions and assistant rule and change proposals use the project’s cross-process write lock. A regression test starts a separate rule-proposal CLI while the server holds a checked update open, then verifies both records. [Project lock](../../tools/review_lock.py), [workflow tests](../../tests/test_project_workflow.py)
- **Keyboard navigation to evidence.** Reviewers can follow a finding to its mark and activate the numbered mark to return to its review card. [Evidence navigation](../../app/invoice-review.js)

- **Finding decisions and reasons.** Chromium verified keyboard selection through the four outcome choices, tabbing to the reason, a reason-only edit, reset, confirmation, and retrying a failed save with the entered reason intact. The review controls disable while a save is pending. An outdated revision keeps the local edits and asks the reviewer to reload. [Finding editor and review save](../../app/invoice-review.js)

- **Invoice project scope.** Chromium verified two projects with the same invoice ID. After a failed switch to B, the view cleared A’s rows, detail and batch actions and offered a retry for B. The old row issued no request. Retrying loaded B, and late A and B responses could not change the view after another switch. [Project activation](../../app/app.js#L33), [invoice loading and selection](../../app/invoice-review.js#L14)
- **Inbox project scope.** The original browser reproduction switched from project A to B, simulated a failed B setup fetch and clicked the old A proposal. Its request went to B. Chromium now shows Retry without the old proposal after the same failed switch. Current Setup clears the old body, guards out-of-date loads and binds decisions to the loaded project and draft. [Project activation](../../app/app.js#L33), [setup load](../../app/project-setup.js#L18), [Inbox decisions](../../app/project-setup.js#L201)
- **Assistant settings.** The original editor silently discarded its draft on navigation or a delayed save, and its six Claude selects had empty accessible names. Chromium now shows named controls, a leave confirmation that preserves the draft when canceled, and disabled inputs during a delayed save. [Settings editor](../../app/workspace-tools.js#L79), [shared leave guard](../../app/workspace.js#L136)
- **Navigation and approval controls.** The original unnamed Help dialog was replaced with a page under the main navigation. Settings uses subsection controls for Export, History and Assistant settings, matching Project setup. Setup now exposes the selected subsection and uses named Inbox actions for individual decisions. The old status filter and status toggles were removed. [Page structure](../../app/index.html#L66), [Settings focus management](../../app/app.js#L94), [Setup navigation and decisions](../../app/project-setup.js#L102)
- **Setup creation and saved edits.** Add invoice type, Add field and Add a rule open named dialogs with their own Add and Cancel actions. The rule editor keeps its title and actions on one sticky row. Chromium verified that Done returns focus to the originating Rules entry, editing enables Discard and Save changes, and restoring the original content returns the editor to Done. Setup prevents editing while its save request is pending. [Setup save bar](../../app/project-setup.js#L79), [Add dialog](../../app/project-setup.js#L337)

## Shared component work

Keep the native buttons, forms and disclosures, along with the small `el()`, `button()`, `pill()` and `promptButton()` helpers. History already shares its row renderer with Export. Setup row content, invoice findings and settings can keep their local markup because their data and actions differ. Prioritize shared behavior for scoped loading and retry, dirty and saving state, upload outcomes, and dialog naming and focus. [UI helpers](../../app/workspace.js#L25), [history renderer](../../app/workspace-tools.js#L18), [history export](../../app/workspace-exports.js#L80)

Consolidate CSS as those components change. The invoice list, detail surface and grid have base rules and later overrides. The styles for `.invoices-layout`, `.detail-head`, `.page-nav` and `table.fields` have no matching current renderer. Keep one definition per component, remove stale selectors after checking all surfaces, and use the existing tokens for shared control states. [Base styles](../../app/app.css#L55), [review layout overrides](../../app/app.css#L198)

## Dropdown inventory

| Where staff see it | Choices | Decision and rationale |
| --- | --- | --- |
| Workspace header · Project | One per local project, plus a prompt when no project is selected | **Keep.** Names and counts vary, and one compact control leaves room for New project. Rebuild in alphabetical order while keeping the active project selected. [Project picker](../../app/app.js#L16) |
| New project · Starting setup | Standard fields, bundled template, and one copy option per local project | **Keep.** The list grows with the workspace. Sort all choices by their display labels and keep Standard fields selected by default, including after form reset. [Source options](../../app/app.js#L26) |
| Invoice review · Finding outcome | Passed, Failed, Unclear, Does not apply | **Keep a visible color-coded selector at the top of each editable finding.** The current choice, original assistant judgment and reviewer reason are visible together when an outcome changes. Staff can also edit the reason alone or reset the finding. The automatic duplicate-number warning stays read-only. [Finding editor](../../app/invoice-review.js) |
| Project setup · Inbox, Rules and Fields to extract filters | All types plus all configured invoice types | **Keep.** This is one filter per view with a project-dependent choice set. All types allows staff to return from a specific filter and to see entries with older type associations. [Type filter](../../app/project-setup.js#L122) |
| Rule editor and Add rule dialog · Invoice type | Every invoice type plus all configured types | **Keep.** The list grows with the project. Every invoice type is a distinct rule scope that also covers future types. [Rule inputs](../../app/project-setup.js#L153) |
| Rule editor · How it is checked | Six check methods | **Keep.** The long labels would occupy several rows, and the method determines which inputs appear. [Check labels](../../app/project-setup.js#L5) |
| Rule editor and Add rule dialog · Field | A field prompt plus zero or more fields for the selected type and rule method | **Keep.** Field names and counts vary. Keep the prompt first and retain the saved field selection on load. [Rule field](../../app/project-setup.js#L164) |
| Rule editor and Add rule dialog · If it fails | Error or warning | **Replace with labeled radios.** Both effects are visible while editing one rule, and the saved severity remains selected. [Rule severity](../../app/project-setup.js#L153) |
| Add field dialog · Invoice type | One choice per configured type | **Show the type as text when there is exactly one choice.** Save its ID directly. Keep the selector for multiple types and explain the required first step when no type exists. [Add field](../../app/project-setup.js#L312) |
| Fields to extract and Add field dialog · Kind of value | Text, amount or date for every field | **Use radios.** The Add dialog shows the three choices directly and starts with Text. Existing fields use a disclosure labeled with the current kind so the radios appear only while editing that field. [Add field kind](../../app/project-setup.js#L331), [existing field kind](../../app/project-setup.js#L409) |
| Assistant settings · Claude model | Three alternatives per job, nine choices across three controls | **Keep.** The table already has three repeated job rows, and model descriptions are long. Sort by label and retain each job’s saved model. [Model controls](../../app/workspace-tools.js#L87) |
| Assistant settings · Claude effort | Five alternatives per job, 15 choices across three controls | **Keep.** A radio group in every row would make the table much taller. Sort each list by label and keep the saved effort. [Effort controls](../../app/workspace-tools.js#L93) |
| Assistant settings · Codex effort | Five alternatives | **Keep.** This uses the same scale and interaction as the three Claude effort controls. The Codex model remains a text input. [Codex controls](../../app/workspace-tools.js#L127) |
| Export · Checked invoice | Zero to many checked invoices | **Show the filename directly when there is exactly one choice.** Keep the selector and initial prompt for longer lists. Preserve a selected invoice when it is available. [Invoice export](../../app/workspace-exports.js#L27) |

Remaining dropdowns use the displayed label and compare base letters in the browser locale. Numbered labels sort in numeric order within the same name. Only genuine prompts are pinned above the sorted choices. The Invoice types view uses the same ordering on a copy for display and keeps the stored type array and IDs intact. [Shared sort](../../app/workspace.js#L24), [Invoice types view](../../app/project-setup.js#L395)

Chromium verified sorting with mixed case, accents and numbers, a rebuilt project picker, the New project reset default, and saved model and effort values. It also verified the saved payloads for rule severity, an existing field kind, the Add field dialog and an invoice override. With one checked invoice, Export showed the filename directly. With several, it showed a prompt first, sorted the filenames and kept the selected invoice. The Invoice types view sorted the cards while leaving the submitted type array in its original order.
